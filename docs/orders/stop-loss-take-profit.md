# 停損停利提醒（一張單兩價位）

> 狀態：尚未實作。本文件描述待開發需求，不是目前 API 或 schema。
> 前半為白話說明，後半〈工單細節（補充）〉為完整設計與驗收條件。

## 一句話

**這張工單 = 讓使用者用一張單同時設「跌破 X 提醒我」和「漲到 Y 提醒我」，先到哪邊就通知哪邊，通知完這張單就結束。**

---

## 現況與缺口

現在已經有 9 種策略（買賣到價、限價買賣、移動出場、市價、TWAP）。缺的是**保護持股**這件事。

具體缺兩塊：

1. **「跌破某個固定價格」這個方向根本沒有。** 移動出場雖然也是往下看，但它的觸發價是從最高點回檔算出來的，不是使用者自己指定的固定價。
2. **就算用兩張現有的單去湊也不對。** 你掛一張「跌到 90 通知我」加一張「漲到 120 通知我」，跌到 90 通知你之後，那張漲到 120 的還活著——你已經打算賣了，它還在等，之後又跳出來吵你一次。

---

## 這張工單做的事（白話）

**1. 一張單，兩個價格，都要填**

「我手上有這檔股票，跌到 90 我要知道，漲到 120 我也要知道。」兩個價格填在同一張單裡。

**2. 先到的那個通知你，這張單就結束**

不會有「通知完還留一半」的狀況，因為本來就是同一張單。

**3. 只做「手上有股票」的情況**

放空的鏡像版本（跌到目標是獲利、漲上去是虧損）之後要做再加，這次不做。

**4. 兩個防呆**

- 停損價一定要低於停利價，填反了直接擋下來。
- 沒填滿兩個價格也擋下來。

**5. 建單當下就已經符合條件 → 直接通知你**

你設「跌到 90 提醒我」，但按下建立時股價已經是 88 了。這時不擋你，讓你建立成功，然後**馬上發一則通知**告訴你「它已經在 88 了」。

理由：這跟其他 9 種策略的行為一致（不用為了這張單做特例），而且既有的立即觸發機制直接就能用，不用多寫東西。

---

## 這張票跟舊版差在哪

舊版的做法是**開兩張單綁成一組**（業界叫 OCO，二擇一）：一張停利、一張停損，再開一張「群組表」把它們綁起來，然後要處理一堆連動問題——一張觸發了要去取消另一張、使用者取消時不能只取消一半、萬一兩張同時被打到要怎麼辦。

現在改成**一張單兩個價格**之後，這些問題整組消失：

| 舊版要處理 | 現在 |
|---|---|
| 群組表、兩張子單 | 一張單就好，沒有群組概念 |
| 一張觸發了要去取消另一張 | 同一張單結束，另一邊自動沒了 |
| 不准只取消一半 | 結構上就沒有「一半」 |
| 兩邊同時被打到怎麼辦 | **不可能發生**（見下） |

**為什麼不可能同時被打到？**

因為我們強制停損價要小於停利價，而兩邊都是看同一個「買價」在判斷：

- 停損：買價 **跌到 90 以下**
- 停利：買價 **漲到 120 以上**

同一個價格不可能同時小於 90 又大於 120。所以舊版那套「同時觸發要標異常、發異常通知、通知管理員」的機制，這裡不是延後做，是**根本不需要存在**。

---

## 常見疑問：這不是跟「賣出到價提醒」重複了嗎？

停利那一邊的判斷方式，確實跟現有的「賣出到價提醒」一模一樣。但整張單提供的東西是現有策略拼不出來的：

- **往下的那個方向本來就沒有**（固定價的停損，現在完全沒有）。
- **兩邊綁在一起、一邊到了整張就結束**——分開掛兩張做不到，會多吵你一次。

而且使用者心裡想的也不一樣：「賣出到價提醒」是**我想在這個價位賣掉**，停損停利是**我在保護我的持股**。同一個判斷式，兩種意圖。

---

## 資料要存在哪（白話版）

現在的設計是「核心表放每張單都有的東西（誰、哪支、幾張、什麼狀態），各策略專屬的參數放各自的小卡片」。

停損停利要存的東西：**停損價、停利價、以及觸發時記下是哪一邊觸發的**。

- 這三樣**開一張新的小卡片**放，不塞進現有那張「目標價」的卡片——那張只有一個價位欄，而且被四種策略共用，硬塞第二個價位進去會讓「目標價」到底是指哪個變得說不清楚。
- 「觸發時是哪一邊」也記在這張小卡片上，不去動大家共用的觸發紀錄表——不動共用的東西，就不會影響現有 9 種策略。

---

## 這次**不做**的事

| 不做 | 原因 |
|---|---|
| 真的去下單 | 現在是三階段的第一階段：只通知。等券商帳號到手才做第二階段 |
| 放空方向 | 之後要做再加，現在不預留欄位 |
| 檢查你到底有沒有這檔股票 | 使用者說有就有，接了券商才談驗證 |
| OCO 群組那一整套 | 一張單兩價位之後不需要了 |
| 通知一定送達的保證 | 那是通知交付保證（outbox）的事，見 [已知技術債](../technical-debt.md) |

## 順帶記一筆：未來要下單的方向

組長 2026-08-19 定調：**停損停利不管是通知還是下單，都我們自己做**——自己盯著報價、自己判斷、觸發後自己送委託給券商，**不把洗價外包給富邦的條件單功能**。

這個決定的好處：

- 富邦的停損停利必須綁在一張新的委託上、而且要等那張單完全成交才開始監控——**對你已經持有的股票根本掛不上去**。自己做就沒這個限制。
- 觸發後送出去的是一般委託，可以帶我們自己的識別碼，券商的回報回來能精準對上是哪一張單。

代價（組長已知並接受）：**我們的服務掛掉或重啟的期間，沒有人在盯**。緩解方式是重啟後第一筆報價進來就會重新判斷一次，所以漏掉的是斷線那段時間的價格穿越，不是整張單失效。

⚠️ 這段只是記錄方向，**這張票不實作，也不預留任何下單用的欄位**。

### 背景

V0.5 已交付 9 種策略（買賣到價、限價買賣、移動出場、市價三種、TWAP）與 evaluator（`src/app/domain/quote_evaluation.py`）。缺的是**持股保護**：使用者手上有股票，想同時設「跌破 X 我要知道」與「漲到 Y 我要知道」，而這兩個是同一個決定的兩面——先到哪邊，另一邊就沒有意義了。

既有策略拼不出這件事：

| 既有策略 | 判斷式 |
|---|---|
| `buy_price_alert` / `limit_buy_order` | `ask <= 目標價` |
| `sell_price_alert` / `limit_sell_order` | `bid >= 目標價` |
| `trailing_stop_alert` | `bid <= 動態觸發價`（自高點回檔算出，非固定價） |

- 「跌破固定價」這個方向**既有 9 策略完全沒有**（移動出場是動態價，不是使用者指定的固定價）。
- 就算用兩張獨立的單湊，一張觸發後另一張仍然有效，會再發一則使用者已經不想要的通知。

### 與舊設計的差異（為什麼重寫）

舊設計成形於 06-03 收斂當時，形狀是 **OCO 群組 + 兩張子單**：新開群組表、一腳觸發連動取消另一腳、單腳取消要整組取消、兩腳同時成立要標 `ambiguous_trigger`。

2026-08-03 改為一張單兩價位、2026-08-19 確認兩價皆必填之後，**「二擇一」變成單列的內建語意**，上述機制整組不需要：

| 舊設計要做 | 現在 |
|---|---|
| 群組表 + 兩張子 intent | 一張單，不需要群組概念 |
| 一腳觸發 → 連動取消另一腳 + 稽核 | 同一列進終態，另一邊自然失效 |
| 「不允許只取消一腳」 | 結構上不存在單腳 |
| 兩腳同時成立 → `ambiguous_trigger` + 異常通知 + admin warning | **結構上不可能發生**，見〈為什麼不需要 ambiguous_trigger〉 |
| `position_side` 推導 order_side、四象限觸發 | 本票只做持有（多單），兩個判斷式 |

### 目標

1. **新增一種策略**（一張單、兩個價位）：停損價與停利價**皆必填**。沿用 8/03 慣例的策略識別字串與 endpoint（`POST /trade-intents/stop-loss-take-profit`，T2 per-strategy 形狀）。
2. **觸發方向**（只做持有／多單，皆為賣出視角，故兩邊都看 bid）：
   - 停損：`bid <= 停損價`
   - 停利：`bid >= 停利價`
   - 缺 bid 時 fallback last 並標記 `fallback_used`（沿用既有慣例）。
3. **建立驗證**：停損價必須小於停利價，違反則拒絕建立（422）。
4. **立即觸發**：建單當下條件已成立（例如設「跌到 90」時現價已是 88）→ **允許建立**，並立即觸發、存 quote snapshot、發通知。沿用既有立即觸發路徑（`tests/test_create_immediate_trigger_integration.py`），零額外機制。
5. **一次觸發即終結**：任一邊成立，整張單進終態，另一邊不再評估、不再通知。
6. **記錄觸發的是哪一邊**：通知文案與後續稽核都要能分辨停損 / 停利。
7. **去重**：同一使用者、同標的、同交易日、同數量，且停損／停利價組合相同 → 視為重複委託，擋下。

### 非目標

- **不做下單**。現況為三階段的階段①（僅通知），本票不加 notify/order 欄位、不加確認狀態、不接券商下單路徑（見〈未來下單方向〉）。
- **不做放空方向**。放空的鏡像判斷屬列舉式擴充，未來要做時另加，不在本票預埋欄位。
- **不驗證真實持倉**。使用者聲明即可，接券商後才談驗證。
- **不做 OCO 群組表、子單、單腳取消、sibling 連動取消、`ambiguous_trigger`**（見上表）。
- **不碰既有 9 策略、不碰共用觸發紀錄表、不碰舊軌**（新軌 only）。
- 不做漲跌停 / 當日限制檢查（V1 已延後）。
- 不做通知交付保證（transactional outbox 與重試 worker，見 `docs/technical-debt.md`〈通知交付為 best-effort〉）。

### DB / 介面

> 顆粒度：本節只定「要存什麼、要擋什麼」，**不定表名、欄位名、CHECK 名稱與錯誤碼字串**——那些施工時照既有三張衛星表的慣例取。

- **新軌 only**：核心表 `trade_intent_core` 的策略枚舉**加一個值**（不是停損、停利兩個——兩價必填代表一張單就是一組）。
- **新增一張本策略專屬的 1:1 衛星表**（`trade_intent_id` 同時當 PK + FK，同既有三張衛星表慣例），存：
  - 停損價、停利價（兩者 NOT NULL）；
  - 觸發後回填「觸發的是哪一邊」。
- **為什麼不共用既有的價格參數表**：那張表只有一組目標價、且被到價／限價四個 endpoint 共用，塞進第二個價位會讓 `target_price` 的語意變模糊。新開窄表正是衛星表分層「加策略＝加一張窄衛星表、核心表不長欄位」的預期用法。
- **為什麼「觸發哪一邊」記在自己的衛星表、不加在共用觸發紀錄表**：不動共用表就不影響既有 9 策略；且「參數表存執行期回填值」在移動出場衛星表的 baseline 系列已有先例，不算破例。
- **去重**沿用核心表既有的 `dedup_key` 單欄機制（存「停損價:停利價」的標準化組合），維持單表唯一索引，不新增跨表索引。
- 數量、交易日、`time_in_force`、`transaction_mode`、`notification_mode` 等共用欄一律沿用既有慣例，本票不新增共用欄。
- **通知**：沿用既有通知路徑（日後改走 outbox 時只改交付層、不改業務語意），文案需分辨停損 / 停利。

### 為什麼不需要 `ambiguous_trigger`

建立時已強制**停損價 < 停利價**，而兩邊都以同一個 bid 判斷：

```
停損成立：bid <= 停損價
停利成立：bid >= 停利價   （停損價 < 停利價）
```

同一個 bid 不可能同時滿足兩者。**同 tick 雙邊同觸在結構上不可能**，因此舊設計的「兩腳同時成立 → 標異常 + 發異常通知 + admin warning」整段刪除，不是延後、是不存在。

### 為什麼不算跟 `sell_price_alert` 重複

停利側的判斷式（`bid >= 目標價`）確實與 `sell_price_alert` 相同。但**兩價必填**之後，本策略提供的是既有策略拼不出來的東西：

- 「跌破固定價」的方向本來就沒有（見〈背景〉）。
- 「一張單同時守住上下兩個邊界、任一邊成立即整張終結」——用兩張獨立的單湊，一張觸發後另一張仍活著，會多發一則使用者已不想要的通知。

使用者心智模型也不同：`sell_price_alert` 是「我想在這個價位賣」，本策略是「我在保護我的持股」。這是可接受的重複。

### 未來下單方向（記錄用，本票不實作、不預埋）

2026-08-19 組長定調：**停損停利不管通知或下單，都由我方自己完成**——自己訂閱報價、自己洗價，觸發後自己對券商送委託。**不使用**富邦條件單（`single_condition` + `TPSLWrapper`）把洗價外包出去。

- 連帶不需要：intent ↔ 富邦條件單號（guid）對照表、輪詢 `get_condition_order` 拿 `ConditionStatus`、盤後 `get_condition_history` 對帳。
- 好處：觸發後送的是**一般委託**，可用 `user_def`（≤10 英數字）帶我方識別碼，`set_on_order` / `set_on_filled` 回報能精準對回單張委託，不必靠輪詢兜底；另外富邦的 TPSL 必須綁在新母單、母單成交才啟動監控，**對既有庫存掛不了固定停損停利**，自己做沒有這個限制。
- 已知代價（組長已定調接受）：我方服務斷線／重啟期間沒有保護。緩解是重啟後第一筆報價即重新評估（與立即觸發同一套邏輯），漏的是斷線期間的價格穿越，不是整張單失效。
- 送單型態（屆時再定，此處僅記錄常規）：**停損要的是確定性**（市價單，或以跌停價掛限價賣出——有價格地板又保證留在委託簿），**停利要的是價格**（限價單掛在停利價，沒成交就繼續持有）。兩者委託參數不同，代表送單那層要依「觸發的是哪一邊」分歧——這正是本票要在衛星表記下觸發邊的原因之一。

### 待確認（不阻塞本票）

- 「兩邊都必填」是 2026-08-19 組長裁定（理由：單純）。先前分析過的「至少填一邊」方案（依據：富邦 `TPSLWrapper` 的 tp / sl 在四種語言綁定加期貨版全部標成 Optional，且真實情境「我怕它跌，但漲了想繼續抱」被強迫填停利價會製造假通知）留存於此，作為**未來若要放寬**的依據；本票不做單邊。

### 驗收條件

- [ ] 建單需同時提供停損價與停利價，缺任一邊拒絕建立。
- [ ] 停損價 ≥ 停利價 → 拒絕建立（422）。
- [ ] 停損觸發（`bid <= 停損價`）與停利觸發（`bid >= 停利價`）方向正確；缺 bid 時 fallback last 並標記。
- [ ] 任一邊觸發 → 整張單進終態，另一邊不再評估、不再發第二則通知。
- [ ] 觸發後可查出「觸發的是停損還是停利」，通知文案據此區分。
- [ ] 建單當下已成立 → 建立成功 + 立即觸發 + 存 quote snapshot + 發通知（不回 422）。
- [ ] 重複委託（同 owner / 標的 / 交易日 / 數量 / 價格組合）被擋下。
- [ ] 既有 9 策略行為與共用觸發紀錄表不受影響。
- [ ] `make check` 全綠。

### 測試要求

- **Unit**：兩個觸發方向 + fallback 標記；停損價 < 停利價的建立驗證；去重鑑別值的標準化（數值相等的價格映射到同一 key）。
- **Integration**：
  - 建單 → 核心 row + 衛星 row 同 transaction 寫入，失敗一致回滾。
  - 停損先到 / 停利先到各一次，驗整張單終態 + 觸發邊記錄 + 只發一則通知。
  - 觸發後再進報價不重複觸發、不重複通知。
  - 立即觸發（建單當下已跌破停損價）→ 建立成功並觸發。
  - 重複委託被擋。
- **Migration**：upgrade 後新衛星表就緒、核心表策略枚舉含新值；downgrade 可還原。

### 工程注意事項

- 一律走**新軌**（`trade_intent_core` + 衛星表 + robot #2 dispatcher），不碰凍結的舊軌持久層。
- evaluator 只加一個策略分支；共用的報價驗證、交易時段、報價新鮮度檢查沿用既有前置，不另寫一套。
- 衛星 row 與核心 row 同 transaction 寫入，沿用既有 repository 慣例（不另 commit）。
- 熱查詢（dispatcher / list / cancel / lifecycle）維持只掃核心表，不因新衛星表退化。
- 觸發邊的回填走既有「evaluator 回傳 → command 落庫」的路徑，不在 dispatcher 迴圈裡直接寫表。
- 命名遵循 snake_case；class 名 PascalCase。
