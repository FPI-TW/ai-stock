# L1 白話說明：身分 / 帳號 / Session

> 這份是 [L1 工單](L1-identity-accounts-session.md) 的白話導讀，給非工程背景的人快速理解「L1 在做什麼、對齊 spec 哪些範圍」。技術細節以工單本體為準。

---

## 一句話

**L1 = 把「單人試用版」改成「多人能安全登入、各看各的」的正式系統。** 它是整個上線計畫的地基，沒有它後面全部動不了。

---

## 現在的問題

App 現在**沒有大門**——程式裡寫死了一個假使用者，所有資料都掛在他身上。等於房子蓋好了但門大開，誰都能進、而且大家共用同一個身分。要給真人用，第一件事就是裝門、發鑰匙、認人。

---

## L1 做的 8 件事（白話）

**1. 真正的登入系統**
做出「輸入帳號密碼 → 進到自己的頁面」，取代寫死的假使用者。

**2. 帳號怎麼來（重點：不開放公開註冊）**
> 管理員開帳號（填 email）→ 系統寄邀請信 → 使用者點連結、自己設密碼 → 帳號啟用。
邀請連結 24 小時有效，過期或重寄舊的就失效。

**3. 保持登入 + 自動續期**
登入後給一張「短效門票」（15 分鐘過期，較安全），背後用一張「長期通行證」自動換新門票，不用一直重登。有人偷走通行證想重複用，系統會察覺並把整條作廢。

**4. 忘記密碼**
使用者可自助重設。防護細節：不管 email 存不存在都回一樣的訊息（避免壞人試探哪些 email 有註冊）。重設成功後舊登入全踢掉。

**5. 兩種身分：一般使用者 vs 管理員**
分清楚誰是普通人、誰是管理員。權限判斷集中一處寫，未來細分角色才不會散落。

**6. 資料隔離（每個人只看得到自己的）**
授權核心：A 絕對不能看/動 B 的提醒。後端永遠從「你登入的身分」決定資料屬於誰，**不信任前端傳來的身分**。

**7. 管理員要用兩階段驗證（2FA）**
管理員權限大，除密碼外還要手機驗證碼。沒設 2FA 就進不了管理功能。（驗過一次就能用，個別操作不再重驗。）
目前 L1 只做「設定 2FA」和「驗證 2FA」；2FA 重設功能尚未存在，只預留資料欄位與撤銷原因，完整流程留待後補。

**8. 登入防爆破**
同一 email 連續輸錯 5 次，鎖 15 分鐘，防止機器狂試密碼。

## 對齊 domain-spec 的範圍

L1 主要切自 **§13（使用者、角色與權限）**，加上 §16、§20 的相關條文。逐項對照：

| L1 做的事 | 對齊 spec 出處 |
|---|---|
| 帳號建立流程（admin 建 → invited → 首登設密 → active） | §13 lines 692–698 |
| Invitation 連結 24h / 只 admin 重寄 / 重寄失舊 / 寫 audit | §13 lines 700–706 |
| Password reset（不洩漏 email、token 30min、重設後撤 session、rate limit） | §13 lines 708–716 |
| Session / JWT 短效 + refresh rotation + reuse 偵測 + CSRF/cookie | §13 lines 718–738 |
| 密碼規則 MVP（≥8 字元，不強制組合） | §13 lines 739–744（規則細節硬化在 L3，L1 套用） |
| 登入防爆破（email 5 次鎖 15min、token-bucket、IP 限流） | §13 lines 746–753 |
| 角色 user / admin、權限檢查集中 | §13 lines 755–760 |
| User 能做 / Admin 能做 | §13 lines 762–774 |
| **Admin TOTP 2FA**（首次啟用後強制；reset 尚未實作，需另一 admin/離線的完整流程留待後補） | §13 line 777 |
| 停用帳號 cascade（取消 intents、停 binding、撤 refresh、保留歷史） | §13 lines 784–792 |
| 真 owner scoping（從 auth context 取 user id、不接受 client 傳 owner、cross-user forbidden） | §13 lines 682–690、§16 owner scope |
| 接受條款版本（invitation accept 帶 termsVersion、寫 audit） | §20 line 1130 |

**一句話**：L1 幾乎等於把 domain-spec **§13 整節**做成可執行的工單，再接上 §16 的 owner 隔離與 §20 的條款接受。

## L1 的邊界（不做什麼、交給誰）

| 不做 | 交給 |
|---|---|
| 跨 endpoint 通用限流（L1 只接登入自己的） | **L2** |
| admin 監控 dashboard / 資料覆寫 / kill switch | **P5** |
| Telegram 綁定（寄信走抽象介面、stub） | **P3** |
| user 端 2FA（只預留欄位） | 後續版本 |
| 通知通道設定 | **P3** |

---

## L1 與 L2 的分工（無佔位、不重工）

這是單人專案、L1→L2 順序進行，沒有「兩人平行、互相等」的問題，所以**不做「先用簡易版佔位、之後再換真」的接力**（那只會白寫一次再拆掉）：

- **稽核紀錄**：L1 **直接建正式紀錄表**，一開始就寫真的；L2 與後續功能沿用同一張表，把各自的事件（誰建提醒、誰按緊急停止鈕…）寫進去。
- **防爆破計數器（RateLimiter）**：L1 做好**正式引擎**、先給登入用；L2 把同一顆引擎擴到所有會動到資料的操作（是擴大使用範圍，不是重做）。

---

## 做完 L1 之後

- 真人可以**被管理員開帳號、收信、設密碼、登入**
- 每個人**只看得到自己的**提醒（資料隔離）
- 管理員有 **2FA** 保護
- 登入有**防爆破**

**但還沒能上線**——還要 L2（防護紀錄 + 緊急停止鈕）和 L3（安全部署）才齊。L1 是地基。
