# P2.5：補齊 intent 生命週期稽核事件（§17，接於 P2 之後）

## Metadata

- 分層：上線後（observability 補完，非阻擋上線）
- 優先序：P2.5（**排在 P2 Outbox 之後**，與 trigger 路徑 refactor 同波）
- ROM：**S**
- 依賴：L2（`audit_events` 真表 + `AuditEventWriter` + create/cancel command 已 plumb `request_id`）、P2（`intent_triggered` 寫在 refactor 後的 outbox 觸發 transaction）
- 交付版本：V1
- 併自舊工單：BE-V1-16-audit-rate-limit-retention（§17 intent 生命週期事件殘留部分）

## 背景

`docs/domain-spec.md` §17 列出 V1 audit log「最低事件集」，其中五個 intent 生命週期事件：`intent_created`、`intent_activated`、`intent_triggered`、`intent_expired`、`intent_cancelled`。

L2（`L2-platform-guard.md` line 41）把這份清單標註為「由各票分別寫入既有表」，並只負責寫自身的 `kill_switch_enabled`/`kill_switch_disabled`。後續拆票時，P1 接走 `oco_sibling_cancelled`、P2 接走 `notification_sent`/`notification_failed`、P4 接 `corporate_action_adjustment_applied`、P5 接 `admin_override_applied`——但**這五個核心 intent 生命週期事件沒有任何活躍工單認領**，程式碼現況 `grep` 也確認完全沒寫。本票收掉這個孤兒，把 §17 的 intent 子集補齊。

L2 已先把 `request_id`（§16 correlation id）plumb 進 `CreateTradeIntentInput` / `CancelTradeIntentInput`，本票直接消費這個已就位的 seam，不需再改 command 介面。

## 目標

在五個既有狀態轉換點，透過 L1 `AuditEventWriter` 寫入既有 `audit_events`，**與該轉換的業務 transaction 同批寫入**（不另開 tx、不另 commit），失敗時一致回滾：

| 事件 | 轉換點（程式錨點） | `actor_type` | `actor_id` | `request_id` 來源 |
|---|---|---|---|---|
| `intent_created` | `CreateTradeIntentCommand.execute` commit 前（`commands/trade_intent.py`） | `user` | owner_user_id | `CreateTradeIntentInput.request_id`（已就位） |
| `intent_cancelled` | `CancelTradeIntentCommand.execute`（`commands/trade_intent.py`） | `user` | owner_user_id | `CancelTradeIntentInput.request_id`（已就位） |
| `intent_triggered` | 觸發 transaction（`commands/trigger_intent.py`；P2 後為 outbox transaction） | `system` | null / 固定 system id | P2 outbox `correlation_id` |
| `intent_activated` | `IntentLifecycleCommand.run` → `system_activate_scheduled_day_intents`（`commands/intent_lifecycle.py`） | `system` | null / 固定 system id | 排程批次 id |
| `intent_expired` | `IntentLifecycleCommand.run` → `system_expire_day_intents_through` | `system` | null / 固定 system id | 排程批次 id |

- 五欄位齊全（`actor_type` / `actor_id` / `occurred_at` / `metadata` / `request_id` 或 correlation id），對齊 §17。
- `metadata` 只放必要轉換脈絡（`symbol` / `strategy` / status 轉換），不含敏感資料。

## 非目標

- 不重建 `audit_events` 表（L1/L2 已建）。
- 不寫其餘 §17 事件：`oco_sibling_cancelled`（P1）、`notification_sent`/`notification_failed`（P2）、`corporate_action_adjustment_applied`（P4）、`admin_override_applied`（P5）、`account_*`（L1）、`kill_switch_*`（L2）——避免重複寫入。
- 不做 audit 查詢 / 匯出 API、不做 retention / 匿名化（P6）。
- 不改 intent 狀態機與業務語意（只加觀測）。

## DB / 介面

- **無新表**，沿用 `audit_events` + `AuditEventWriter`。
- **bulk 轉換需逐筆 audit**：`intent_activated` / `intent_expired` 來自批次 SQL（`system_activate_scheduled_day_intents` / `system_expire_day_intents_through`），目前只回傳受影響筆數。本票需讓這兩個 repository 方法回傳受影響的 intent id（`UPDATE ... RETURNING id`），讓 lifecycle command 能逐筆寫 audit（避免 N+1：一次 RETURNING 取回後批次寫入）。

## 依賴與交接

- 依賴 L2 `request_id` seam（create/cancel Input 已有 `request_id` 欄，由 routes/intents.py 注入）。
- **與 P2 協調 `intent_triggered`**：本票排在 P2 之後，`intent_triggered` 寫在 P2 refactor 後的 outbox 觸發 transaction 內，`actor_type=system`，沿用 P2 的 outbox `correlation_id`，避免對 `trigger_intent.py` 改兩次。
- `system` 事件 `actor_id` 慣例：依現有 audit 寫入慣例，system 觸發無 user actor → `actor_id` 留 null 或專案既定 system id（與其他 system 事件一致）。

## 驗收條件

- [ ] 建單成功 → 寫一筆 `intent_created`（`actor_type=user`、`actor_id=owner`、`request_id` 帶入）。
- [ ] 取消成功 → 一筆 `intent_cancelled`（`actor_type=user`）。
- [ ] 觸發 → 一筆 `intent_triggered`（`actor_type=system`）。
- [ ] 日內 scheduled→active 批次 → **每筆**受影響 intent 各一筆 `intent_activated`（筆數 = 受影響 intent 數）。
- [ ] 日內到期批次 → **每筆** `intent_expired`。
- [ ] 五欄位齊全；audit 與業務 transaction 同批，失敗一致回滾（建單失敗 → 不留 `intent_created`）。
- [ ] 不與既有事件重複（`oco_sibling_cancelled` 仍只由 P1 寫）。

## 測試要求

- Unit：各 transition 寫對 `event_type` + `actor_type`；bulk activate/expire 受影響筆數 == 寫入 audit 筆數。
- Integration：create → `intent_created`（含 `request_id`）；cancel → `intent_cancelled`；trigger → `intent_triggered`；批次 activate/expire 各筆寫 audit；建單 rollback 不留 audit。

## 工程注意事項

- audit 與業務寫入同一 transaction，沿用 `AuditEventWriter`（不另 commit），與 L1/L2 既有寫入慣例一致。
- bulk activate/expire 用 `RETURNING id` 一次取回受影響 id 再批次寫 audit，避免 N+1。
- `metadata` 只放必要欄位（symbol / strategy / status 轉換），不放敏感資料（§17 工程約束）。
- `system` 事件無 `request_id` 時填 correlation / 排程批次 id（§17：「`request_id` 或 correlation id」）。
