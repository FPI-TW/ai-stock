# P2.5 白話說明：補齊委託的「事件紀錄」

> 這份是 [P2.5 工單](P2.5-intent-lifecycle-audit.md) 的白話導讀。屬**上線後**迭代（接於 P2 後）。

---

## 一句話

**這張票 = 幫每一張委託的「重要時刻」補上一筆事件紀錄（audit），讓事後查得到「誰、在什麼時候、對哪張委託做了什麼」。**

---

## 現況與缺口

spec §17 規定 V1 要有 audit log，並列出五個跟委託有關的「最低必記事件」：

- `intent_created`（委託被建立）
- `intent_activated`（隔日從預約轉成生效）
- `intent_triggered`（到價觸發）
- `intent_expired`（當日到期）
- `intent_cancelled`（被取消）

L2 當初把這份清單標成「由各票分別寫入」，但拆票時：P1 只接走「OCO 連動取消」、P2 接走「通知送出/失敗」、P4 接除息、P5 接 admin 覆寫——**這五個最核心的委託事件，沒有任何一張票接走**，程式碼裡也確實一筆都沒寫。

> 白話：規格說「這五件事一定要記帳」，結果排工作時漏掉了，變成沒人負責的孤兒。這張票就是把它補回來。

而且這跟你之前抓到的「帳號復權」是同一種情況——規格假設有人會做，拆票時掉了。

---

## 這張票做的事（白話）

**在委託的五個關鍵時刻，各補一筆紀錄：**

| 時刻 | 誰做的 | 白話 |
|---|---|---|
| 建立 | 使用者 | 你按下建立委託 → 記一筆 |
| 取消 | 使用者 | 你取消委託 → 記一筆 |
| 觸發 | 系統 | 行情到價、系統觸發 → 記一筆 |
| 啟用 | 系統 | 隔天預約單變生效 → 每張各記一筆 |
| 到期 | 系統 | 當天收盤沒成、到期 → 每張各記一筆 |

每筆都帶齊：誰做的、什麼時候、哪張委託、以及一個可追查的「請求編號」（L2 已經先把這個編號接到建立/取消的流程裡了，這張票直接拿來用）。

---

## 兩個技術重點（白話）

**1. 批次操作也要逐筆記帳**
「隔日啟用」「當日到期」是系統一次處理一大批委託的。目前程式只回報「處理了幾張」，但記帳要的是「哪幾張」。所以要讓它在處理時順手回報每一張的編號，才能逐張寫紀錄——而且要一次撈回來批次寫，不要一張查一次（會很慢）。

**2. 「觸發」這筆要等 P2 之後再做**
P2 會把觸發流程改寫成「先記帳再送通知」（outbox）。觸發的 audit 就寫在那個改寫後的流程裡，這樣同一段程式只改一次，不會 P2 改一遍、這張票又改一遍。

## 對齊 domain-spec 的範圍

| 這張票做的事 | 對齊 spec 出處 |
|---|---|
| 五個 intent 生命週期事件 + 五欄位（actor/time/metadata/request_id） | **§17** lines 1044–1068 |
| 直接用 L2 已就位的 request_id（correlation id） | **§16**（correlation id）+ L2 已 plumb |

---

## 這張票的邊界

| 不做 | 交給 |
|---|---|
| 重建 audit 表 | L1 / L2（已建） |
| OCO 連動取消事件 | **P1**（已負責 `oco_sibling_cancelled`） |
| 通知送出/失敗事件 | **P2** |
| 除息調整事件 | **P4** |
| admin 覆寫事件 | **P5** |
| audit 查詢 API / 保留與匿名化 | **P6** |
| 改委託的狀態機或業務行為 | 不碰，只「在旁邊記帳」 |

---

## 做完之後

委託從「狀態會變、但沒有事件軌跡」變成「每個關鍵時刻都查得到」，補齊 §17 對委託的最低稽核要求。
