# T1 白話說明：把「一張大表塞所有策略欄位」拆成「核心表 + 各策略小卡」

> 這份是 [T1 工單](T1-trade-intent-satellite-params.md) 的白話導讀。屬 **V0.5 遺留的 schema 重構（技術債）**，上線後可獨立排程，不擋上線。

---

## 一句話

**這張票 = 把委託主表瘦身：只留所有策略共用的欄位，每種策略專屬的參數搬去各自的「小卡」表，往後加新策略不必再動主表。**

---

## 現況與痛點

現在所有委託（不管哪種策略）都擠在同一張 `trade_intents` 表，欄位已經膨脹到約 14 個「策略專屬」欄。問題是：

- **一筆資料大半欄位是空的**——限價單的 row，trailing 和 twap 的欄位全是 null，看不出這是哪種單。
- **規則愈疊愈長**——為了限制「某策略才能填某些欄」，主表上塞了好幾條又臭又長的跨欄檢查規則，每加一種策略就要再補一條。
- **加新策略要動主表**——任何新交易手段都得改這張大家共用的主表，舊策略全被連累、有風險。

> 白話：這是 V0.5 當初為了快，把全部策略欄位塞進同一張表留下的債。

---

## 這張票做的事（白話）

**主表只留「每張單都會用到」的共通欄位**（誰的、哪檔股票、哪種策略、數量、狀態、時間…），策略專屬參數則搬到三張「小卡」表：

| 小卡表 | 裝什麼 | 給誰用 |
|---|---|---|
| 價格參數卡 | 目標價（原始 / 生效） | 到價提醒 + 限價買賣（四個入口共用一張） |
| 移動停利參數卡 | 移動模式、幅度、基準、動態觸發價… | 移動停利 |
| TWAP 參數卡 | 多空方向、切片時間 / 數量… | TWAP 分批單 |

- **市價單**沒有專屬參數 → 連小卡都不用配。
- 一張委託最多配一張對應小卡（用委託 id 當小卡的主鍵，資料庫天然保證不會重複）。
- 以後加新策略 = 多開一張小卡表，**主表完全不用動、舊策略零風險**。

---

## 為什麼這樣拆（兩個關鍵取捨）

**1. 為什麼不乾脆拆成 6 張獨立表？**
因為系統最常跑的查詢（找到價的單、列某人的單、取消、隔日啟用、到期）都只看「狀態」、不分策略。拆成 6 張表會逼出一堆 UNION 拼裝，還會打爛 twap 切片、觸發紀錄、通知這些表對委託 id 的關聯。所以保留「單一主表」，需要參數時才去 JOIN 小卡。

**2. 為什麼不把參數塞進一個 JSON 欄？**
那樣加策略最省事，但會失去資料庫層的型別與規則檢查，跟本專案重視 typed / mypy 的風格不合。先不採用，未來策略真的爆量再說。

---

## 舊資料不用搬（已確認）

目前主表裡都是測試資料，所以**不需要把舊資料搬到小卡表**。migration 直接重建結構就好，必要時連同子表一起清空——這省掉了原本這張票最重的一段（資料回填 + 確保不丟資料）。

## 最大的地雷（跟搬不搬舊資料無關，一定要做）

主表現在有兩條「防止重複下單」的唯一規則，它們用到了即將被搬走的欄位（目標價、移動模式、多空方向…）。

**注意**：這條地雷講的是「**以後新下的單**會不會被重複擋下」，不是舊資料——所以就算舊資料不搬，這兩條規則仍然必須**等價地搬到小卡上重建**，否則上線後會放行重複委託。這是這張票風險最高的地方，驗收會逐情境測試。

---

## 這張票的邊界

| 不做 | 原因 / 交給誰 |
|---|---|
| 把 API 入口按策略拆開 | 另一張獨立票（這票只動資料庫和讀寫層） |
| 改委託的狀態流程或業務行為 | 不碰，只搬欄位 |
| 改對外回傳的 JSON 格式 | 維持原樣，由組裝層把主表 + 小卡拼回去 |
| 動 twap 切片 / 觸發紀錄 / 通知 對委託的關聯 | 不碰 |
| 新增策略 | 不在範圍內 |

---

## 做完之後

委託主表從「一張塞滿空欄位的大表」變成「乾淨的核心表 + 各策略小卡」，看資料一眼就懂、加新策略不必動主表，收掉 V0.5 留下的這筆 schema 債。
