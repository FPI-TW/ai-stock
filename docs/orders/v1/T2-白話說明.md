# T2 白話說明：把「一個建單入口塞所有策略」拆成「每種策略各一個入口」

> 這份是 [T2 工單](T2-split-trade-intent-create-endpoints.md) 的白話導讀。屬 **V0.5 遺留的 API 重構（技術債）**，上線後可獨立排程，不擋上線。
>
> **狀態：程式已實作於分支 `feat/split-trade-intent-create-endpoints`，這份工單是事後補的追蹤文件。**

---

## 一句話

**這張票 = 把「一個萬用建單入口」拆成「每種策略各有自己的入口」，前端送什麼欄位、後端怎麼驗，一眼就清楚，不用再靠 `getattr` 猜。**

---

## 現況與痛點

V0.5 的建單只有一個入口 `POST /trade-intents`，不管你要下到價提醒、限價單、市價單還是移動停利，都丟進同一個「什麼欄位都可能有、也什麼都可能沒有」的大表單。後端只好用 `getattr` 一個個去挖「這個策略到底帶了哪些欄」。

- 前端 / API 文件看不出「這個策略該填哪些欄」——因為每個欄位都是選填。
- 後端取值靠猜，型別不收斂、容易漏驗。
- 加一種新策略，又得往這個大表單塞更多選填欄、再加一條 if。

> 白話：跟 T1（資料表塞太多欄）是同一個病，只是這次長在「API 入口」上。

---

## 這張票做的事（白話）

**每種策略開一個專屬入口**，每個入口只收「這種策略真正需要的欄位」：

| 新入口 | 用途 |
|---|---|
| `POST /trade-intents/buy-price-alert` | 買進到價提醒 |
| `POST /trade-intents/sell-price-alert` | 賣出到價提醒 |
| `POST /trade-intents/limit-buy-order` | 限價買單 |
| `POST /trade-intents/limit-sell-order` | 限價賣單 |
| `POST /trade-intents/market-order` | 市價單 |
| `POST /trade-intents/trailing-stop-alert` | 移動停利 |

- TWAP 本來就有自己的「預覽 + 確認」兩步流程，不動它。
- 舊的萬用入口 `POST /trade-intents` **先留著**，等前端都改用新入口後再另票退場。
- 六個入口共用同一段「防重複送出 + 真正建單 + 組回應」的程式，不會各寫一份。

---

## 跟 T1 的關係（別搞混）

| | T1 | T2（這張） |
|---|---|---|
| 動哪裡 | 資料庫（核心表 + 衛星表） | API 入口 |
| 解決什麼 | 一張表塞太多策略欄 | 一個入口塞太多策略欄 |
| 動單表嗎 | 會（搬欄位） | **完全不動 DB** |

兩張票各做各的、互不依賴，任何順序都行。

---

## 這張票的邊界

| 不做 | 原因 / 交給誰 |
|---|---|
| 改資料庫結構 | T1 負責 |
| 改建單的業務邏輯 | 不碰，入口只負責把表單攤平交給原本的建單命令 |
| 拿掉舊的萬用入口 | 等前端遷移完再另票退場 |
| 動取消 / 查詢 / TWAP 流程 | 不碰 |

---

## 做完之後

每種策略的建單入口型別清楚、欄位收斂，前端與 API 文件一看就懂；加新策略 = 開一個新入口，不必再往萬用大表單塞選填欄。
