# 產品定位與演進方向

## 產品定位

AI Stock 是「事件驅動的通知與條件下單系統」的公版基底。目前產品處於 demo／需求驗證階段，現行能力是盯盤與通知，不是自動化量化交易平台。

公版採單租戶、單機部署。未來客戶差異透過各自的程式碼分支增減，不建立同一套 runtime 同時服務多客戶的多租戶、feature flag 或外掛平台。現存 auth、admin、2FA、session 與 rate limiter 可繼續運作，但不因過去的訂閱制構想而主動擴充。

## 現況

- Web API 可管理交易意圖與站內通知。
- Telegram 以單一 `TELEGRAM_CHAT_ID` 群組作為 demo 輸入管道，可建立限價買賣與市價買賣意圖。
- 系統監控行情並在條件成立時通知；所有 intent 固定為 `notify_only`，不呼叫券商下單 API。
- 行情 runtime 目前使用 Shioaji demo provider；`in_memory` provider 僅供測試與 CI。
- 部署規模是單機與個位數至數十檔標的，PostgreSQL 同時承擔資料、鎖與排程協調所需的持久化責任。

## 下單能力演進

下單方向採三階段，每次只實作當前階段，不為下一階段預埋欄位或狀態：

1. **目前：僅通知。** 條件成立後產生通知，不送出委託。
2. **通知後確認下單。** 使用者在觸發後確認，才送出券商委託；屆時才定義待確認與逾時語意。
3. **建單時授權直接下單。** 使用者建立意圖時明確授權，條件成立後直接送單；屆時才決定是否保留第二階段模式。

未來第一個下單整合預定採富邦新一代 API（Fubon Neo），預設使用測試環境，真單環境以設定切換。每套部署只連一個券商帳號，不做 per-user 券商帳號綁定。Shioaji 是否保留尚未定案，不可假設已退場。

## 核心能力與近期缺口

現行策略包含到價、限價、市價、移動出場與 TWAP；TWAP 目前仍由舊持久層承載。持倉型停利／停損尚未實作，需求見 [停利／停損工單](orders/stop-loss-take-profit.md)。語音輸入尚未排程；若未來實作，應使用既有 STT／LLM 服務把文字轉為同一套 typed intent，不自建 NLP 平台。

## 設計紅線

- 所有買賣行為必須源自使用者明確建立、確認或授權的交易意圖；系統不得自行決定買賣。
- 不做回測、策略最佳化、高頻交易或微秒級延遲工程。
- 新增交易方式採明確列舉與 typed schema，不建立動態策略 registry、plugin system 或策略工廠。
- 判斷觸發與執行動作需解耦；只有一家券商時直接使用具體 client，等第二個實作出現再抽象介面。
- 不引入 Kafka、Redis cluster、時序資料庫或多帳號輪替。需要 queue、lock、cache 時優先使用 PostgreSQL 與 process-local cache。
- 券商的訂閱與速率上限是外部硬限制；達上限時清楚拒絕，不建立配額平台或動態擴容。
